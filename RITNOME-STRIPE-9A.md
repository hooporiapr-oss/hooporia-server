# Ritnome Stripe webhook intake — Phase 9A, disabled
This module is intentionally NOT mounted or deployed. It leaves the existing /webhook and all current invoice processing unchanged.
Future route: POST /ritnome/stripe/webhook, express.raw({type:'application/json'}) before express.json().
Use separate RITNOME_STRIPE_WEBHOOK_SECRET, RITNOME_STRIPE_PRICE_ID, RITNOME_STRIPE_LIVEMODE and a server-side Stripe client authorized for the correct account/mode. Do not commit real secrets or live identifiers. Require explicit opt-in and fail closed if missing.
Inbox adapter contract: isTracked(subscriptionId, livemode) returns boolean based on persisted facility/subscription binding; enqueue atomically inserts a minimal event reference with unique (livemode,stripe_event_id), returning success on duplicates and throwing on storage failure. No license writes at intake. A worker must reconcile from current Stripe data, validate price/quantity/customer/facility binding, serialize changes per subscription, verify paid invoices and entitlement expiry and handle changes/cancellations and failed payments. No card data, customer email, raw webhook payload or license secrets in inbox. Do not activate from checkout completion alone. Storage and worker are pending, as are checkout and real Stripe sandbox tests. Do not enable in production until permission hardening and end-to-end tests pass.
Run local mocked tests: node ritnome-stripe-webhook.test.js. Test uses fake signature verification and an in-memory Map; does NOT validate real Stripe signatures, SQL deduplication, concurrent writes or actual lifecycle.
Docs: https://docs.stripe.com/webhooks and https://docs.stripe.com/billing/subscriptions/webhooks
